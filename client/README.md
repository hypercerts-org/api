# @hypercerts-org/api

TypeScript query definitions and types for the Hypercerts API, for use with [`@atproto/lex`](https://www.npmjs.com/package/@atproto/lex). Not published to npm yet; use it from this workspace or a git dependency.

```ts
import { Client } from "@atproto/lex";
import { getActivity, listBadgeAwards, type ActivityView } from "@hypercerts-org/api";

const api = new Client("https://api.hypercerts.dev");
const { activity } = await api.call(getActivity, { uri });
const { badgeAwards, cursor } = await api.call(listBadgeAwards, { authors: [did], limit: 50 });
```

## What it contains

- One query definition per endpoint, exported by its short name (`getActivity`, `listBadgeAwards`). `Client.call` uses it for the NSID, the parameters and response validation.
- The types of each query's parameters and views (`ActivityView`, `OrganizationActorView`). Each query and defs Lexicon is also exported as a namespace for the types every query shares or that more than one Lexicon defines differently: `GetActivity.$Params`, `GetBadgeDefinition.BadgeDefinitionView`, `ApiDefs.ProfileView`.
- `LEXICON_VERSION`: the `@hypercerts-org/lexicon` version the definitions were generated from, also in `package.json` as `hypercerts.lexiconVersion`.

Records embedded in views are typed from a generated copy of the record Lexicons. Once `@hypercerts-org/lexicon/records` exists (TECH-750), they will be imported from there instead.

ESM only. `@atproto/lex` is a peer dependency.

## Response validation

`Client` validates responses against the Lexicons by default. The indexer may still serve records that fail their Lexicon, and one such record fails a whole list response. Until it stops doing so (TECH-791), read with `new Client(url, { validateResponse: false })`.

## How it is generated

`pnpm generate` (or `pnpm client:generate` from the repository root) runs `lex build` over the Lexicons declared in `api/manifest.json` `validationLexicons`: the API's query Lexicons from `api/lexicons/` and the record Lexicons they reference, read from the repository-pinned `@hypercerts-org/lexicon` package. It writes `src/lexicons/` and `src/index.ts`, and records the Lexicon version in `package.json`. Generated files are committed; do not edit them.

Regenerate whenever a query Lexicon, `api/manifest.json` or the pinned Lexicon package changes. `pnpm check:generated` fails when the committed output is stale.

The generator works around [bluesky-social/atproto#5738](https://github.com/bluesky-social/atproto/issues/5738), broken imports for queries under a record NSID. Remove the workaround once it is fixed upstream.

## Commands

Run from `client/`:

| Command                                           | What it does                                                                                  |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `pnpm generate`                                   | Regenerate `src/`                                                                             |
| `pnpm check`                                      | Freshness, lint, format check, type check, build and tests                                    |
| `pnpm lint` / `pnpm format` / `pnpm format:check` | Biome; only `format` rewrites files                                                           |
| `pnpm build`                                      | Compile to `dist/`                                                                            |
| `pnpm test`                                       | Build, then load the built package and call queries through a `Client` with a stubbed `fetch` |

Tooling follows the SDK repository (TECH-748): Biome, TypeScript 7, ESM, Node 24 or later. `exactOptionalPropertyTypes` is off because code generated by `@atproto/lex` 0.4.2 does not compile with it.

## Versioning

The package is not versioned or released yet: it is listed in the Changesets `ignore` list, because the release workflow only tags the API module bundle. Releases start when the workflow supports more than one package.
